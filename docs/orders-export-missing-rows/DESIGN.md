## 1. The task in one paragraph
Finance reports that the nightly order export wrote 47,961 rows while `GET /orders/count` said 48,213. The export
pages through a Flask orders API with an opaque `next_cursor`. The cursor holds only the last row's `created_at`, and
the next page asks for `created_at < ?`, so whenever a page ends inside a group of orders that share one second (bulk
imports write hundreds at once) the rest of that group is skipped. The same predicate is copied, inline, into the
customer listing (`GET /customers/<id>/orders`). The agent must find the cause and fix both listings so that following
`next_cursor` returns every order exactly once, in the documented order (`created_at DESC, id DESC`), with the
documented page sizes, also while other processes insert orders. The verifier walks the agent's service over HTTP on a
hidden 30,000-order database.

## 3. Data (FACT: `authoring/orders-export-missing-rows/gen_data.out.md`)
- **Visible** (seed 317): 48,213 orders, 4,600 customers, 962 same-second groups, largest 62. The buggy walk loses 252
  orders at limit 200 (47,961 exported, the ticket's numbers), 466 at 100, 916 at 50, 84 at 500 (the ticket's note).
  Customer listings: at the default limit 100 no customer loses an order (FACT, our count on 2026-10-28 with the
  buggy-walk model of `gen_data.py`); at the support tool's limit 20, 19 customers do, 18 of them wholesale. The ticket names the
  worst one, computed by `gen_data.py`: wholesale account 5 has 61 orders and the shipped listing shows 20.
- **Hidden** (seed 90210): 30,000 orders, 3,100 customers, 867 same-second groups, 21 of them with 100 to 380 orders,
  23 among the newest 2,000 rows; 1,500 backfilled orders (highest ids, dates in the first nine months), 302 groups that
  mix an old low id with a backfilled high id. The buggy walk loses 4,209 orders at limit 50, 1,349 at 200, 924 at 500,
  1,626 within the newest 5,000 at limit 7, 1,370 within the newest 2,000 at limit 1. `gen_data.py` asserts each is
  above 0.
- **Test customers** (`plan.json`): six wholesale accounts with 190 to 413 orders (per customer, the buggy walks at
  limits 3 and 20 together lose 341 to 736 rows), two retail customers with backfilled orders, two with
  marketplace-import ties (these four lose 0 or 1 row in the original; they check the order around backfilled orders,
  not the tie bug); customer 320 has no orders; 4100 does not exist.
- **Orders inserted during walks** (`plan.json`, built by `make_inserts()` in `gen_data.py`; ids 30,001 to 30,056 in
  write order). `/orders` walk at limit 100, 25 orders after page 3 and 25 after page 10. Each batch: orders newer than
  every stored order (batch 1: an EDI import of 10 orders for customer 6 in one new second; batch 2: 6 checkout orders,
  2 per second); 1 order in the second of the last order of the page just served; 10 or 12 late-synced orders
  (`pos_backfill`: high id, old date) in distinct seconds of stored orders at positions 5,000 and later; 4 or 6 in
  distinct seconds the walk has already passed. Then customer 6's walk at limit 3 (the customer listing as it stands
  after the 50 inserts, 436 orders), 3 orders after page 2 and 3 after page 5: one in the second of the last order
  served, late-synced ones behind and ahead of the walk, one new order. `gen_data.py` asserts that no batch-1 order
  lands between the end of page 3 and the end of page 10, so every valid fix ends page 10 on the same order. By
  channel: 10 `edi_import`, 4 `pos`, 35 `pos_backfill`, 7 `web`.
- 30,000 is a multiple of 50, 100, 200 and 500, so a fix that sends a cursor after a full last page gets an empty last
  page, and a fix that fetches `limit + 1` does not. API.md allows both and the grader accepts both (canonical walks
  61 pages at limit 500, alt 60; FACT, grade logs of our local runs on 2026-10-28).

## 4. The verifier
`test.sh` (kit) runs `python3 -I /tests/grade.py` as root. grade.py:
1. Logs the Python and SQLite versions; checks SHA256SUMS; loads the hidden database (root's own file, `immutable=1`)
   and computes the expected order twice (Python sort and SQLite `ORDER BY created_at DESC, id DESC`; they must agree);
   `kit.prepare_submission()`.
2. **Original phase** (before any agent code runs): stages `tests/original` and a database copy for uid 1001, starts the
   original (`python -m orders_service --db <copy> --port <p>`), records `/orders/count` and `/orders/<id>` for the
   300 sample ids. They must equal the database, or grading stops with a grader error.
3. **Agent phase** (another fresh copy; the agent's service from `/work/sub`, same command; one keep-alive connection,
   one retry per request, 10 s per request, 30 s to start, one 900 s budget for all requests):
   - c7 public suite, HTTP-only: default page (100 newest, a cursor), count, one order, `limit=500`, a customer's default page.
   - c1 order: walks of `/orders` at limit 50, 200 and 500 (all 30,000), limit 7 over the newest 5,000, limit 1 over
     the newest 2,000. Ids must equal the expected order exactly.
   - c2 pages: every page but the last holds exactly `limit`; null cursor on the last page only; an empty last page is
     fine. A repeated cursor or more than `ceil(n / limit) + 2` pages stops the walk as a failure.
   - c3 customers: each test customer at limits 3 and 20; the customer without orders gets an empty page.
   - c5 errors: `limit` = 0, 501, -3, `ten`, `2.5` and cursors `not-a-cursor`, `!!!` get 400 on `/orders`; `limit=0`
     and a bad cursor get 400 on a customer listing; an unknown order and an unknown customer get 404.
   - c6 fields: every order in every walk equals the database on the API.md fields; `/orders/<id>` for 300 sample ids
     equals the original's answer.
   - c4 inserts: a walk of `/orders` at limit 100; after page 3 and page 10 a helper run as uid 1001 (`python3 -I -S
     -c`, our code) inserts 25 orders each into the database file (section 3: new orders, one in the second just
     served, late-synced orders ahead of and behind the walk). Then a walk of customer 6's orders at limit 3 with 3
     orders inserted after page 2 and 3 after page 5. In each walk, every order that existed when it started must
     come back exactly once and in order, no inserted order twice, no id outside that listing. Then a fresh walk at
     limit 150, two customer walks and `/orders/count` must include all 56 inserted orders exactly; two inserted
     orders are read back by id. The follow-up checks run only when all 56 inserts succeeded (the count comes from
     `plan.json`); otherwise c4 has already failed.
4. **db**: after the service is stopped, uid 1001 copies the database (and its `-wal` file, if any) into root's
   scratch folder; root opens that copy, checks that `sqlite_master` lists `orders` and `customers` as tables, and
   compares `orders` (all seven columns) and `customers` with the hidden data plus the 56 inserted rows.
5. Reward 1 only if every check passed at least once and failed never. `reward.json` holds `<check>_ok` (1 or 0) per
   check, `failed_checks`, `agent_seconds`, `grading_seconds`; test-stdout shows up to 40 failures.

Leniency (G13, G15), each stated in or allowed by the instruction: only API.md fields are compared (extra fields are
fine; the instruction says "at least the fields in `API.md`"); one retry per request after a timeout or a lost
connection (stated); any cursor string is accepted; both last-page behaviours pass; an order inserted during a walk may
or may not appear in that walk (the canonical shows the 22 late-synced orders ahead of the `/orders` walk, the
`snapshot_bound_valid` ablation shows none; both score 1); tables, columns or indexes the agent adds are ignored by the
read-back.

What a service sees (rule 8 of `base/verifier_kit/README.md`, G21): the agent's service runs as uid 1001 with the host network (the kit gives
services no private namespace), its own copy of the hidden database (which is what it serves) and the grader's
requests. It cannot read `/tests`. The insert helper also runs on the host network (a service is live). INFERENCE: a
hostile service could send the hidden database out over the network; that would not raise its own score, but it would
spoil the hidden data for later runs.

## 6. Deviations from the original design (with reasons)
The original design is our brief for this task and the shared verifier rules for all five tasks, written and approved
before the build (not shipped). Where a rule matters below, its wording is given.

- **Ticket numbers kept by a seed search.** With the hidden data's mix the visible export lost 3,585 of 48,213 (FACT,
  first generation), far from the ticket's 252 and not a "silent" loss. The visible database now has fewer, smaller
  groups (at most 60 per import); of the 365 seeds tried (1 to 365), seeds 240 and 317 lose exactly 252 at limit 200
  (FACT, our seed search on 2026-10-28; output not saved in a file); 317 was taken. The hidden database keeps the hard mix.
- **Inserts go into the database file, not through the API.** The API is read-only by contract, and a start-up
  snapshot (attempt G) must be caught; a POST could refresh a snapshot. The helper is our code run as uid 1001, so root
  never opens the agent's files.
- **Added the db read-back check.** Without it attempt H (rewrite `created_at` at start-up, strip it in responses)
  passed c1-c3 and c5-c7. The instruction states the rule ("must not change stored data") and allows added indexes.
- **Check (7) is HTTP-only** (five requests mirroring `tests/test_api.py`); the agent's pytest is never run, because a
  pass written by agent code is not evidence (rule 4 of `base/verifier_kit/README.md`).
- **Three attempts added** to the design's A-F: G (snapshot), H (rewrite at start-up), I (AND predicate, a common
  wrong keyset condition).
- **Error cases** are the ones the shipped service already answers (FACT, our curl requests to it on the visible
  database, 2026-10-28),
  so a correct fix that leaves parsing alone keeps them.
- **One budget for the agent phase** instead of per-run caps. The shared cap rule says: "Each run of agent code has a
  `grade.py` cap of 3 × the measured slowest valid solution (usually the alt); `verifier.timeout_sec` = sum of the
  caps + measured grading time + 50%". Here all requests go to one live service, so there is one budget.
  Timings and the derivation are in section 8.
- **Runtime.** 1 CPU and 2048 MB as designed. "Verifier under 2 min" in the brief is the expected run time (3.3 s on
  the Mac); `verifier.timeout_sec` is the cap from the shared cap rule's formula (section 8).
- **Row values.** The canonical uses `(created_at, id) < (?, ?)`; the alt avoids row values. The Mac's SQLite is 3.53.4
  (FACT, grade log). The image's SQLite version is UNVERIFIED (INFERENCE: Debian bookworm's libsqlite3; row values exist
  since SQLite 3.15.0). grade.py logs `sqlite3.sqlite_version`; if the oracle fails on Daytona, swapping
  `keyset_clause()` to the OR form is a one-line change.
- **Review fixes (an independent review on 2026-10-28, section 9; we checked each finding before applying it).**
  - *c4 was weaker than the instruction (high).* Both insert batches held only orders newer than every stored order,
    and orders were inserted only during an `/orders` walk. Three plausible wrong fixes (J, K, L) passed the visible
    tests and scored 1 (FACT, reproduced by our own run with the grader as first built, `docs/orders-export-missing-rows/before_review/`). Fixed: the batches now
    hold same-second and late-synced orders (section 3), customer 6's walk gets inserts, and the attempts are in the
    package. This needed no new rule: API.md already says late-synced orders have a high id and an old date, and
    that every order existing at the first page comes back exactly once.
  - *Fields (low).* The instruction said "the same fields and values"; the grader compares the API.md fields only.
    The instruction now says "at least the fields in `API.md`". Tightening the grader instead was not needed: an extra
    field breaks no client.
  - *Page size 500 (low).* The instruction says walks use page sizes up to 500, but 500 was only a first page. A full
    walk at 500 is added (61 pages, 0.10 s).
  - *Retry (low).* The grader sends a timed-out or dropped request once more, which the instruction did not say. The
    retry is kept and stated: it protects valid fixes from a one-off stall on an unknown sandbox (G16); dropping it
    would make a single slow moment decide the reward.
  - *Tables (low).* The read-back now requires `orders` and `customers` to be tables in `sqlite_master` (a view with
    an INSTEAD OF trigger would have passed); the instruction says they must stay tables.
  - *Ticket clue (low).* The ticket said the support tool showed a wholesale account with fewer orders, but at the
    default page size no customer loses an order (section 3). The ticket now names the support tool's page size (20)
    and the account (5: 20 of 61 shown), computed by `gen_data.py`.
  - Each change kept the databases, the log and `tests/original` byte-identical (FACT: sha256 of every package file
    before and after the `gen_data.py` re-run; only `INCIDENT.md`, `plan.json` and `SHA256SUMS` changed).

  the shared cap rule (section 6) sets each cap at 3 x the slowest valid solution measured. The naive fix returns correct pages,

## 9. Known limits and open issues
- The naive full-load fix is the only solution whose Daytona time decides whether the budget is right, and it is a
  local-only ablation (`ablations.py`), so the planned proof matrix never measures it. Running it once on Daytona
  (apply the ablation by hand to a copy) would show whether 900 s holds.
- (Written before the Daytona run; superseded by section 12, 2026-10-29: every row as expected, J, K and L 0.0.) Not
  run on Daytona yet: the "(run)" gate items wait for the proof matrix (oracle × 10, alt, nop, the twelve
  attempts, oracle with `--force-build`). J, K and L matter most there: with the grader as first built they scored 1,
  so G12 rests on their Daytona result. Each attempt run must show `applied <attempt> to /app` in
  `agent/oracle.txt`; otherwise the variable did not reach `solve.sh` and the run proves nothing. The proof run must show in test-stdout: `[kit] python 3.12.x, sqlite <version>`,
  `[test.sh] lock ok`, `[kit] reward=...`, and `agent_seconds` in reward.json. The `network isolation` line of `base/verifier_kit/README.md`
  will not appear for this task: every runner process here runs while a service is live, so the kit never probes
  for a private network namespace.
- The shared rules ask that "a second reader writes the expected checks from the instruction alone before a verifier
  is final". An independent review did this on 2026-10-28: the reader wrote the checks expected from `instruction.md` and `environment/` before opening `tests/`,
  then compared them with grade.py. Every expected check was there; the differences it found are fixed (section 6,
  "Review fixes"). Inside grade.py the expected order is still computed two ways (Python sort and SQLite).
- Inserts during a customer walk are tested on one customer (6) at one page size (3). The fixes that page each listing
  with its own code are the target (L); a fix wrong only at another page size would need another walk.
- The image size is not measured (no Docker on the Mac). INFERENCE: the slim base plus about 15 small pure-Python
  packages, well under 200 MB.
- The hidden database and the visible one are generated by the same code with different seeds and settings; an agent
  that read `gen_data.py` could predict their shape, but it is not in the package.
- Easy for strong agents (the main risk named in the brief): "A low pass rate by itself is not a sign of quality"
  (the assignment, "How we will review"). The second code path, the backfilled ids and the insert semantics are where weaker fixes fail.
